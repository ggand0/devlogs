## What to build first for 0.4.0

Order differs slightly from 008: trash delete first, then the EXIF
panel, then RAW previews. The chapter for 0.4.0 is the first culling
pass: seeing shots at speed, reading EXIF, trashing the rejects.
Ratings are the second pass and can be 0.5.0.

1. Trash delete while navigating. Small. The trash crate is MIT. The
   real work is index bookkeeping: panes hold a path vector plus a
   current index, and the sliding window, thumbnail and LRU caches are
   all keyed on file index. That same plumbing is what a rating filter
   needs later, so it is not throwaway. Lands the one user who said this
   is the only thing blocking a switch (Netroxen, #36).
2. EXIF footer and sidebar. Medium. kamadak-exif 0.6.1 is BSD-2 and
   reads JPEG, TIFF-based files, HEIF, PNG and WebP. Nothing EXIF-related
   exists in the codebase yet. Answers the largest group of requests and
   is the panel where a rating widget lives later.
3. RAW via embedded JPEG preview. Medium, self-contained. Zero
   third-party decoder. See the licensing section.
4. NAS repro rig. One evening, then unknown. Not a feature, a bug class.
   Set up a local NFS export with added latency and run a 1.6k-file
   folder before shipping to r/DataHoarder. Measure first, scope after.
5. Dual-pane sync fix. Small. Do it whenever pane code is touched.

Ratings with XMP sidecars and filter wait until the panel exists and
until the owner has talked to Andrew, because nobody knows yet whether
he rates in-app or in his SQLite tool.

## RAW licensing

The 008 claim that a license problem stopped the iced RAW attempt could
not be confirmed. The iced branch feat/raw-formats has three commits
using libraw-rs 0.0.4, was never merged, and carries no note about why.
Treat it as a working note.

Verified on crates.io on 2026-09-11:

| Crate | Version | License |
|---|---|---|
| libraw-rs (bindings) | 0.0.4 | MIT/Apache-2.0 (LibRaw itself is LGPL-2.1 or CDDL-1.0) |
| rawler | 0.8.0 | LGPL-2.1 |
| rawloader | 0.37.2 | LGPL-2.1 |
| quickraw | 0.2.1-alpha.1 | LGPL-2.1 |
| kamadak-exif | 0.6.1 | BSD-2-Clause |
| trash | 5.2.8 | MIT |

How the licenses differ, in one line each: MIT/Apache/BSD ask for the
notice only. LGPL covers the library only; the app keeps its own
license, but the library source must be available and the user must be
able to relink. GPL 2 and 3 would spread to the whole binary. CDDL is
file-scoped copyleft, so static linking is fine.

Consequences:

- Embedded previews need no decoder at all: own TIFF and ISO BMFF
  parsing plus kamadak-exif. Clean in every build.
- If real RAW decoding comes later, rawler behind the official flag is
  legally fine because the app source is public. The GitHub Releases
  build never contains it, so it carries no obligation. The official
  build on Polar then needs two extra files next to the binaries: a
  THIRD-PARTY-LICENSES.txt naming rawler, its version, a link to the
  release tag and the crates.io source, plus the full LGPL 2.1 text; and
  the rawler source tarball for that version. No .so, no app archive.
- LibRaw is not planned. Build burden across three toolchains, not the
  license, is the reason.
- Preview size caveat, to verify on real files with exiftool: Sony ARW
  embeds a 1616 by 1080 preview; Canon CR3 and Nikon NEF carry a
  full-size JPEG. Andrew shoots ARW.

Both RAW previews and later decoding go behind the official flag. From
the user's side both are "RAW support"; the release notes say previews
are what is displayed.

## Trash delete: what the trash crate does

Verified against the trash 5.2.8 source, not the README.

`trash::delete(path)` never unlinks the source on its own. The only
`remove_file` calls in the crate are: (a) inside the Linux cross-device
fallback, after a successful copy into the trash folder, when `rename`
failed with `CrossesDevices` (bind mounts, btrfs subvolumes); the file
still ends up in the trash; (b) in `os_limited::purge_all` and restore
bookkeeping, which we never call.

Per platform:

- Linux (freedesktop): if the file is on the same mount as
  `~/.local/share/Trash`, it is renamed there. Otherwise the crate
  looks for `$mount/.Trash/$uid` and falls back to creating
  `$mount/.Trash-$uid` at the mount root, then renames into it. This is
  what Nautilus does on an NFS or Samba share too, so NAS users will see
  a `.Trash-1000` directory appear on the share. If the mount root is
  not writable, `create_dir` fails and the crate returns an error with
  the file untouched.
- Windows: `IFileOperation` with `FOF_ALLOWUNDO | FOF_NO_UI |
  FOF_WANTNUKEWARNING`. `FOF_ALLOWUNDO` means Recycle Bin. Network
  paths (UNC or mapped drives) have no Recycle Bin on Windows, so the
  shell deletes them permanently. `FOF_WANTNUKEWARNING` partially
  overrides the no-confirmation flag and should show the Windows
  "permanently delete?" dialog first. NOT VERIFIED on a Windows machine;
  must be tested before release because Windows is the largest platform
  and the NAS persona lives there. viewskater must guard this itself:
  detect remote drives (`GetDriveTypeW == DRIVE_REMOTE` or a UNC
  prefix) and show its own confirmation, never rely on the shell.
- macOS: default `DeleteMethod::Finder` runs an AppleScript that asks
  Finder to delete. It supports Put Back and plays the sound, but needs
  Finder running and triggers the Automation permission prompt
  ("ViewSkater wants to control Finder"). `DeleteMethod::NsFileManager`
  calls `trashItemAtURL`, is faster, needs no prompt, no Put Back. On a
  network volume without a trash, `trashItemAtURL` returns an error and
  the file is untouched. Decision pending; NsFileManager is the safer
  default for a culling loop.

## Trash delete: design

Key: Delete on every platform, plus Cmd+Backspace on macOS (Finder
convention). No confirmation dialog on local disks; the point of
culling is speed and the trash is the undo. A confirmation only when
the destination cannot recycle (Windows remote drive).

Order of operations, per pane action:

1. Call `trash::delete` on `image_paths[current_index]`. On `Err`,
   log, show the error in the footer, change nothing.
2. On `Ok`, remove the path from `image_paths`. The current index now
   points at the next image; if the last file was deleted, step back
   one; if the list is empty, close the pane content.
3. Fix every index-keyed structure. All three caches key on file index,
   so every index above the removed one shifts down by one:
   - `SlidingWindowCache`: remove the slot at
     `removed - first_file_index` if inside the window, push a `None`
     at the back and spawn a load for the new rightmost file. Remap
     `running_decodes`, `pending_decodes` and `pending_uploads` (drop the
     removed index, decrement the rest). If the removed index is left
     of the window, decrement `first_file_index`.
   - Stale results: a decode thread already running for index k > i
     will report k, which now names a different file. `DecodeResult`
     has no path. Add the path to it and have `poll` drop results
     whose path no longer matches `image_paths[file_index]`. This
     also closes a pre-existing race in `jump_to`.
   - `DecodeLruCache` and `ThumbnailCache`: both `HashMap<usize, _>`.
     Add a `remove_index(i)` that drops i and shifts higher keys,
     keeping `order` and byte totals consistent.
4. Dual pane: if the other pane shows the same directory (synced mode
   opens the same `dir_path`), apply the same removal to it. In
   independent mode with a different directory, only the active pane
   changes.
5. Footer shows "Moved to Trash: name" for a few seconds.

Rule for the whole codebase: `std::fs::remove_file` and `remove_dir*`
never appear in the app. The only deletion path is the trash crate.

  Nothing changes unless the trasher returns Ok.
- `src/app/culling.rs`: `trash_current_images` (active panes, one move

  `trash_paths` (the showing pane moves through `remove_current`, every

  Edit menu gets "Move to Trash  Del". Keyboard is blocked while the
  confirmation modal is open.

## Explanations that were missing from the code and this log

Window: the `2 * cache_count + 1` decoded images the sliding window
cache keeps, the current image plus `cache_count` on each side. With
the default Cache Size of 5 that is 11 images. `first_file_index` is
the index of the leftmost.

When each `remove_index` case happens. In single pane the trashed file
is always the one on screen, which is always inside its own window, so
only the "inside" case can occur: its slot is dropped, the other ten
images stay decoded, and one file past the window is loaded to fill the
slot. The "before the window" and "after the window" cases only happen
in dual pane: two panes on the same folder, independent mode, the left
pane trashes file 20 while the right pane shows file 50. File 20 has
to leave the right pane's list too, and the right pane's cache sees a
removal it has nothing loaded for. Before: indices shift, nothing is
decoded. After: nothing changes.

Why decode results carry a path, not an index. A thread started for
file 8 may finish after file 8 was trashed, when a different file is
number 8. An index would put the deleted photo in that slot. With the
path, `poll` looks the index up in the `running_decodes` map, which
`remove_index` keeps current, and drops the result if the path is gone.
The size of this change was misreported as small in chat; the path
part is about 15 lines, `remove_index` is the bulk, and the two were
not separated when described.

Why the pane tests use a rename into a tempdir instead of the real
trash. Tests that run on every `cargo test` would fail on a CI box with
no HOME or XDG_DATA_HOME (the crate errors there), and on macOS the
crate cannot list or purge the trash, so test images would pile up.
The real trash is covered by the ignored round trip, run by hand. Using
the real trash in the pane test and restoring afterwards is possible if
the owner prefers it.

The three index-holding lists in `SlidingWindowCache`, in the order an
image passes through them:

1. `running_decodes`: decodes running on a thread now. Capped by the Decode
   Threads setting (default 10). Added when the thread starts, removed
   when its result arrives. Keyed by path so a late result can find its
   current index.
2. `pending_decodes`: files the window wants decoded but no thread is
   free for. When a thread finishes, the next queued file starts if its
   index is still inside the window. Exists because a jump asks for all
   slots at once and starting that many threads together would
   oversubscribe the CPU.
3. `pending_uploads`: decoded pixels waiting to become GPU textures. At
   most `UPLOADS_PER_FRAME` (2) per frame so a burst of finished decodes
   does not stall one frame.

`remove_index` reindexes all three.

Performance of the path change: per decoded image, one hash of the path
when the result arrives and one clone of the path when the thread
starts, roughly a hundred bytes each, against a decode of milliseconds.
No new allocation for the result; the thread already owned the path and
now hands it back instead of dropping it. Not measurable.

How an image moves through the sliding window cache. Everything below
the thread runs on the main thread inside `poll`, once per frame, so
the cache needs no locks; decode threads only open, decode, send one
result and exit.

    request_decode(index, path)          (was spawn_load, renamed 8a45b16)
            |
            +-- no thread free --> pending_decodes [(index, path)]
            |                            |
            |            a thread finishes: poll pops the next one --+
            |                                                        |
            +-- thread free --> running_decodes {path -> index} <----+
                                    |        (was in_flight, renamed 23c4ec1)
                                    v
                              decode thread: open path, decode
                                    |
                                    v  channel tx -> rx
                          DecodeResult { path, image }
                                    |
                                    v
                                  poll()
                    running_decodes.remove(path) -> index (may have shifted)
                                    |
                                    +-- not found --> drop (file was trashed)
                                    |
                                    +-- found --> pending_uploads [(index, image, name)]
                                                        |
                                                        v  at most 2 per frame
                                                  slots[index - first_file_index]

    remove_index(removed): in all three lists,
        index > removed  -> index - 1
        index == removed -> entry dropped

`DecodeResult` itself is never stored. `poll` unpacks it: the path is
matched against `running_decodes`, the pixels go into `pending_uploads`.

## Nautilus "Restore" failure on /data2, 2026-09-12: not the app

Symptom: files the app moved to the trash on /data2 could not be
restored from the Nautilus Trash view ("There was an error moving the
file into ... No such file or directory"). Restoring with `gio trash
--restore`, with Nautilus's own move operation over D-Bus, and with GIO
from Python all worked on the same entries, and the records were valid
(gvfs reported name, origin and date correctly).

Root cause: gvfsd-trash held a stale in-memory item table. An strace of
the daemon during a failing Restore showed no file syscalls at all; the
"not found" came from its table lookup. Every path that worked had
enumerated the trash first, which makes the daemon rescan. Later the
same failure hit files Nautilus had trashed itself, on /data, /data_hdd
and /data2. `killall gvfsd-trash` (it respawns on demand) fixed it:
Nautilus's own Restore From Trash then restored an app-trashed entry.
The machine sits at 120 of 128 inotify instances, which is the likely
reason the daemon's directory watch went dead.

Wrong turns taken before that, for the record: absolute vs relative
Path in the record (both fine), placeholder-then-rename write order
(fine), parentheses in the folder name (fine). Hand-made entries in all
those forms failed the same way while the daemon was stale.

Test plan note: if Restore fails in Nautilus for every entry, including
ones Nautilus trashed itself, restart gvfsd-trash before blaming the
app.
Owner confirmed after `killall gvfsd-trash`: everything restorable from
Nautilus again, including the files the app trashed.

## Bug found on the way: menu clicks toggled pane selection

In independent dual-pane mode, Edit > Move to Trash worked every
other time. Repeated with the same timing five times: pass, nothing,
pass, nothing, pass. The footer glyph never failed, Edit > Preferences
never failed, so the trash code was not the suspect.

Cause: the pane selection strips (the "1" and "2" bars at the top of
the panes, 18 px high) were not egui widgets. app.rs polled
`pointer.any_click()` and toggled the pane whose half of the strip
rectangle contained the pointer, with no regard for what was drawn on
top. The Edit menu's first row spans y 100 to 118 in a window whose
strip spans y 93 to 111, so a click on "Move to Trash" also flipped
pane 1's selection: selected (trash, now deselected), deselected
(nothing, now selected), and so on. The 2026-09-12 test proved it by
clicking the same row at y 115, below the strip: nothing toggled, and
every click trashed once pane 1 was reselected through the strip.
Any menu row over the strip has the same effect (File's first rows,
View's Single Pane), so this predates the trash feature and only
matters in independent mode.

Fix: each strip is now `ui.interact(strip_rect, id, Sense::click())`,
so egui routes the click by layer and a menu popup keeps it. The strip
is added after the divider handle, so it takes the top 18 px of the
handle's grab area; the rest of the handle still drags (checked: pane 1
went from 318 to 388 px wide). Verified live: three menu trashes in a
row each moved one file per selected pane, both strips still toggle,
`cargo test` and clippy clean.

~/.Trash.
